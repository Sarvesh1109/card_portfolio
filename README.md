# Card Portfolio Analytics — RuPay-style product analytics, end to end

An end-to-end analytics project on a **synthetic** card portfolio (5,000 cards, 1,200 merchants, ~146k transactions, one randomised campaign). It covers the full product-analytics loop: governed data → KPIs → segmentation → predictive models → test-and-learn → pricing and unit economics → reporting.

> **All data is simulated.** It is generated by `src/s01_generate_data.py` with a fixed seed. Interchange, reward and cost rates in `src/common.py` are illustrative assumptions, not NPCI or issuer figures. Results demonstrate *method*; none of them is a real-world finding.

## Business questions answered

| # | Question | Where |
|---|----------|-------|
| 1 | How is the portfolio doing — activation, usage, spend, retention, attrition? | `s04`, `sql/02_portfolio_kpis.sql` |
| 2 | Who are our customers and merchants (personas, value tiers, lifecycle, ABC merchant classes)? | `s05` |
| 3 | Which active cards will go silent next quarter, and whom should we call first? | `s06` |
| 4 | Who is most likely to take a premium upgrade (cross-sell)? | `s07` |
| 5 | Did the October reactivation offer cause extra spend, and did it pay back? Who should get it next time? | `s08` |
| 6 | Where do we make or lose money (card × category)? What do reward changes need to achieve to pay off? | `s09` |
| 7 | Can the numbers be trusted? (DQ gate, raw→clean reconciliation, SQL = Python reconciliation) | `s02`, `s11` |

## Run it

```bash
pip install -r requirements.txt
python run_all.py            # ~30 seconds; fully seeded and reproducible
open outputs/dashboard.html  # self-contained management dashboard
```

Python 3.10+. No GPU, no external services, no data download.

## Headline results (synthetic data — see limitations)

* **Data quality:** 5 of 12 checks found issues in the raw feed (duplicates, reversals, ×100 unit errors, nulls); every rupee reconciles raw → clean.
* **Retention:** 90–91% of active cards stay active quarter to quarter (9–10% quarterly attrition).
* **Attrition model:** hold-out AUC 0.889 (gradient boosting) vs 0.874 (logistic baseline); the riskiest 20% of cards contain 72% of attriters. Strongest drivers: recent transaction count, recency, spend trend.
* **Cross-sell model:** hold-out AUC ≈ 0.70 — modest, as expected for an 8% event with noisy drivers; the model is a ranking aid, not a certainty.
* **Campaign (randomised 75/25):** +₹5.2k spend per treated customer (CUPED 95% CI ₹3.3k–₹7.2k; CUPED cut variance 28%). Net value per treated customer is +₹12, but the 95% CI (−₹2 to +₹27) includes zero, and ~90% of the rewards went to customers who would have qualified anyway. Treating only the top 20% by predicted uplift gives the same total value with 80% fewer rewards.
* **Unit economics:** contribution ≈ 0.97% of spend. Select cards **lose** money on Fuel, Grocery and Utilities because their flat 1.0% reward exceeds interchange there. A category-tiered reward redesign adds ~₹205k margin on the same spend (before any behavioural response).
* **Pricing what-ifs:** a +0.25pp Classic reward would need ~31% more spend to break even vs ~6% assumed — rewards alone don't pay for themselves under these assumptions.

## What is deliberately *not* here

No big-data engine (Spark/Databricks), no cloud deployment, no .pbix file (build one from `outputs/powerbi_exports` + `powerbi/measures.dax`), and no real data. See `docs/limitations_and_interview_notes.md` for how to talk about this honestly.
